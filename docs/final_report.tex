\begin{abstract}
Social media platforms must continuously rank a large stream of posts for users with different interests. Production systems often combine follow graphs, engagement histories, freshness, quality signals, and policy constraints, but these signals are difficult to reproduce in a small course project. This paper presents DistribuTweet, a pseudo-distributed content-based recommendation system for Twitter/X-like streams. The implemented demo uses the public Bright Data Twitter/X posts sample, converts CSV rows into an internal tweet feature stream, publishes them to Apache Kafka, cleans and decodes them with Apache Spark Structured Streaming, embeds multilingual text with a sentence-transformer model, stores vectors in Qdrant, and serves personalized feeds through a Scala http4s API. User profiles are created from explicit interest phrases, and feed items are ranked with a transparent formula combining semantic similarity and recency. The implementation runs locally with Docker Compose while preserving distributed-system boundaries: Kafka topics use partitions, Spark runs on a standalone master with workers, embedding consumers run as a shared consumer group, and the API is separated from vector storage. The result is an inspectable end-to-end prototype that demonstrates semantic recommendation, streaming ingestion, vector search, and horizontal scaling concepts on a real public Twitter/X sample.
\end{abstract}

\section{Introduction}
Personalized social feeds are a continuous ranking problem. A platform receives many posts, while each user can consume only a small subset. Pure chronological ordering is simple, but it does not guarantee relevance. Follow graphs and collaborative signals are powerful, yet they require user history, graph data, and large-scale feedback logs. For a course-scale prototype, a content-based approach is a practical baseline: it recommends posts by comparing the meaning of a user's stated interests with the meaning of incoming post text.

DistribuTweet implements this baseline as an end-to-end distributed data path. The project is not only a recommendation formula; it includes data ingestion, messaging, stream processing, embedding, vector indexing, an API, tests, and demo scripts. The current implementation uses Bright Data's public Twitter/X sample repository as the local dataset source \cite{brightdataGithub}. The same data family is also offered in larger marketplace packages, including a Databricks Marketplace listing for Twitter/X posts and profiles at 20 million records \cite{databricksBrightData}. Therefore, the prototype can be demonstrated with a small public sample while keeping a plausible migration path toward larger data exports.

The main contributions are: (i) a reproducible Docker Compose environment with Kafka, Spark, Qdrant, embedding workers, and a Scala API; (ii) a Bright Data CSV adapter that maps public Twitter/X rows into the project's internal stream schema; (iii) a Spark cleaner that parses TSV records, validates them, decodes WordPiece tokens, and deduplicates tweets; (iv) a vector retrieval and ranking layer that exposes semantic, recency, and final scores; and (v) scripts that demonstrate distribution across Kafka partitions, Spark workers, and embedding consumers.

\section{Related Work}
Content-based recommendation systems represent users and items through item attributes and recommend items similar to the user's profile \cite{pazzani2007content}. Hybrid recommenders combine content-based and collaborative signals to improve coverage and accuracy \cite{burke2002hybrid}. Large industrial recommenders commonly separate candidate generation from ranking; for example, YouTube's recommender uses a retrieval stage followed by a ranking stage \cite{covington2016youtube}. DistribuTweet mirrors this separation at a smaller scale: Qdrant retrieves semantically similar candidates, and the API applies a lightweight ranking formula.

The stream-processing architecture builds on well-known distributed systems. Kafka provides a durable publish-subscribe log for decoupling producers and consumers \cite{kreps2011kafka}. Spark provides a unified engine for distributed data processing \cite{zaharia2016spark}. DistribuTweet uses Kafka for the raw and cleaned post streams and Spark Structured Streaming for validation, token decoding, and deduplication.

Semantic retrieval relies on dense sentence representations. Sentence-BERT showed that transformer-based encoders can generate sentence embeddings suitable for efficient similarity search \cite{reimers2019sentencebert}. The implementation uses the multilingual MiniLM sentence-transformer model, producing normalized 384-dimensional vectors. Qdrant stores these vectors and supports cosine search over a collection \cite{qdrantdocs}. Bright Data's Twitter/X dataset pages describe structured post fields such as description text, posting time, hashtags, media, engagement counts, and profile metadata \cite{brightdataProduct}; these fields are appropriate for building a content-based feed prototype.

\section{Implementation Details}
\subsection{Dataset and Adapter}
The default dataset source is the public Bright Data Twitter/X sample repository \cite{brightdataGithub}. The downloaded CSV currently contains 1000 post rows. Its important fields for this project are \texttt{id}, \texttt{user\_posted}, \texttt{description}, \texttt{date\_posted}, \texttt{photos}, \texttt{videos}, \texttt{hashtags}, \texttt{followers}, \texttt{following}, and \texttt{is\_verified}. The source data itself is not committed to the project zip; the paper and README provide the official links.

The sample is a small version of the same type of data offered through larger Bright Data marketplace products. The Databricks Marketplace listing referenced for the project describes a Twitter/X posts and profiles dataset with 20 million records \cite{databricksBrightData}. Bright Data also states that Twitter post datasets can be delivered in formats such as CSV, JSON, NDJSON, and Parquet and can be filtered or customized \cite{brightdataProduct}. This matters because the implemented adapter is not limited to the 1000-row sample. If a larger CSV or Parquet export is obtained for academic research, the same ingestion boundary can be reused with batching and limits.

The adapter maps CSV rows into the internal stream schema. The \texttt{id} field becomes \texttt{tweet\_id}; \texttt{description} is tokenized with \texttt{bert-base-multilingual-cased} and stored as \texttt{text\_tokens}; \texttt{date\_posted} is converted to Unix seconds; \texttt{user\_posted} is hashed into an author identifier; hashtags and media fields become list metadata. The public sample does not contain a normalized language field, so the adapter writes \texttt{und} as a metadata value. The downstream ranking does not depend on this field.

\subsection{Kafka Ingestion}
The \texttt{data-generator} service writes internal TSV records to \texttt{posts.raw}. In the default Docker Compose run, it reads the Bright Data CSV from the GitHub raw URL and publishes the first 1000 rows. The number of processed rows can be changed with \texttt{TOTAL\_MESSAGES}; for example, the same pipeline can process the first 10, 100, or 1000 rows without code changes. The producer uses the tweet ID as the Kafka key, giving stable partitioning and making duplicates observable downstream.

\subsection{Spark Cleaning and Token Decode}
The Spark cleaner consumes \texttt{posts.raw}. It parses each TSV row according to the internal tweet feature schema, rejects malformed records, validates required fields, decodes BERT token IDs back into text using a broadcast \texttt{vocab.txt}, and removes duplicate tweet IDs with event-time watermarking. The cleaner writes accepted records as JSON to \texttt{posts.cleaned}. Its responsibility is deliberately limited to data preparation; it does not make recommendation decisions.

\subsection{Embedding Workers and Qdrant}
The embedding workers consume \texttt{posts.cleaned} using a shared Kafka consumer group. Each valid cleaned post is embedded with \texttt{paraphrase-multilingual-MiniLM-L12-v2}. Vectors are normalized and written to the Qdrant \texttt{posts} collection with cosine distance and size 384. The same Python image also runs as a single HTTP embedding service on port 8000 with consumer mode disabled; the Scala API calls this service when it needs to embed user interest phrases.

\subsection{Recommendation API}
The API runs on port 8081 and exposes:

\begin{itemize}
\item \texttt{POST /users/\{userId\}/interests}: creates a user profile from interest phrases.
\item \texttt{GET /users/\{userId\}/feed?limit=20}: returns a personalized feed.
\item \texttt{GET /health}: returns service health.
\end{itemize}

For profile creation, each interest phrase is embedded, the vectors are averaged, and the average is normalized. For feed retrieval, the API searches Qdrant for similar posts and reranks the candidates.

\section{Recommendation Method}
Let \(\mathbf{e_i}\) be the embedding of interest phrase \(i\). The user profile vector is:

\begin{equation}
\mathbf{u} =
\frac{\frac{1}{n}\sum_{i=1}^{n}\mathbf{e_i}}
{\left\|\frac{1}{n}\sum_{i=1}^{n}\mathbf{e_i}\right\|_2}.
\end{equation}

Qdrant returns cosine similarity scores. The API maps cosine similarity from \([-1,1]\) to \([0,1]\):

\begin{equation}
semantic = \frac{cosine + 1}{2}.
\end{equation}

Recency is computed with exponential decay:

\begin{equation}
recency = e^{-\frac{ageHours}{24}}.
\end{equation}

The final score is:

\begin{equation}
finalScore = 0.85 \cdot semantic + 0.15 \cdot recency.
\end{equation}

The weights are intentionally simple and configurable. This makes the prototype explainable during the demo: every feed item exposes its semantic similarity, recency score, and final score. The feed layer also removes near-duplicate text variants using Jaccard similarity over word sets, preventing visually repetitive feeds when different records contain almost identical content.

\section{Evaluation and Demonstration}
\subsection{Functional Demo}
The main demonstration starts all services with:

\begin{verbatim}
docker compose up -d --build
\end{verbatim}

The \texttt{data-generator} begins replaying the Bright Data Twitter/X sample. The \texttt{scripts/demo.sh} script then walks through the full system: dataset replay, Kafka partition distribution, Spark cleaning, embedding worker group status, Qdrant vector count, and three feed examples for different interest profiles. Health and verification are available through \texttt{scripts/smoke-test.sh}. The distribution proof script, \texttt{scripts/show-distribution.sh}, displays Kafka partition assignment and worker distribution.

\subsection{Observed Behavior}
The system demonstrates that content-based semantic search can retrieve posts related to explicit interests without using a follow graph. In the smoke test, a profile containing phrases such as \texttt{Gaza ceasefire}, \texttt{Palestine solidarity}, and \texttt{human rights} returned posts about Palestine solidarity and related public discussions from the indexed sample. Since the public sample is not balanced by topic and is much smaller than the commercial dataset, the evaluation is functional and qualitative rather than a statistical recommender benchmark.

\subsection{Tests}
Python tests cover Bright Data CSV conversion, offset and limit handling, timestamp parsing, hashtag mapping, and empty-description filtering. The Scala test suite covers internal TSV parsing, validation behavior, WordPiece decoding, ranking score calculations, and deterministic fingerprint behavior. The Docker build includes the Scala tests, so broken core logic prevents image creation. The project also provides smoke tests for the running Compose environment.

\section{Deployment}
Docker Compose is the primary target. The environment starts Kafka, Qdrant, Spark master, two Spark workers, Spark cleaner, data generator, two embedding workers, one embedding API, and the recommendation API. The exposed interfaces include the Spark master UI at port 8080, Spark application UI around port 4040, Qdrant dashboard at port 6333, embedding health at port 8000, and recommendation API at port 8081.

The implementation is pseudo-distributed: all containers run on one machine, but the software boundaries match a horizontally scalable design. Kafka can repartition topics, Spark can run additional workers, and embedding workers can be scaled with Docker Compose. Post vectors are stored outside the API process in Qdrant. User profile vectors are kept in API memory in the current prototype, so multi-replica API deployment would require moving profiles to Qdrant or another shared store.

\section{Limitations}
DistribuTweet does not train a learned ranking model. It does not use collaborative filtering, impression history, authentication, moderation, or private production features. The default public sample contains only about 1000 rows and is not balanced for recommender evaluation. The adapter tokenizes plain CSV text into the internal TSV stream format, but large Parquet exports would require either conversion to CSV or a small Parquet reader extension. Therefore, the evaluation demonstrates system correctness and architectural scalability, not production recommendation quality.

\section{Conclusion and Future Work}
This project implements a working pseudo-distributed semantic recommendation pipeline for Twitter/X-like streams. Kafka decouples services, Spark cleans and decodes internal tweet feature records, the embedding workers index multilingual vectors, Qdrant provides vector retrieval, and the Scala API serves personalized feeds with explainable scores.

Future work should process a larger Bright Data export, incorporate engagement counts as ranking features, train a ranking model, add impression history, evaluate ranking metrics such as NDCG, add stronger diversity controls, monitor latency and Kafka lag, and test a multi-node Kubernetes deployment. If academic access to the 20 million record dataset is obtained, the first technical step would be to run the existing adapter in bounded batches and compare throughput across 1000, 10000, and larger row counts.
