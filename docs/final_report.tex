\begin{abstract}
Social media platforms must continuously rank a large stream of posts for users with different interests. Production systems often combine follow graphs, engagement histories, freshness, quality signals, and policy constraints, but those signals are difficult to reproduce in a small course project. This paper presents DistribuTweet, a pseudo-distributed content-based recommendation system for tweet-like streams. The system generates records compatible with the public RecSys Challenge 2021 Twitter schema, publishes them to Apache Kafka, cleans and decodes them with Apache Spark Structured Streaming, embeds multilingual text with a local sentence-transformer model, stores vectors in Qdrant, and serves personalized feeds through a Scala http4s API. User profiles are created from explicit interest phrases, and feed items are ranked with a transparent formula combining semantic similarity and recency. The implementation runs locally with Docker Compose while preserving distributed-system boundaries: Kafka topics use partitions, Spark runs on a standalone master with workers, embedding consumers run as a shared consumer group, and the API is separated from vector storage. The result is an inspectable end-to-end prototype that demonstrates semantic recommendation, streaming ingestion, vector search, and horizontal scaling concepts without requiring proprietary production data.
\end{abstract}

\section{Introduction}
Personalized social feeds are a continuous ranking problem. A platform receives many posts, while each user can consume only a small subset. Pure chronological ordering is simple, but it does not guarantee relevance. Follow graphs and collaborative signals are powerful, yet they require user history, graph data, and large-scale feedback logs. For a course-scale prototype, a content-based approach is a practical baseline: it recommends posts by comparing the meaning of a user's stated interests with the meaning of incoming post text.

DistribuTweet implements this baseline as an end-to-end distributed data path. The project is not only a recommendation formula; it includes data production, messaging, stream processing, embedding, vector indexing, an API, tests, and demo scripts. The system follows the RecSys Challenge 2021 Twitter dataset schema \cite{belli2021recsys} so that the ingestion layer resembles a realistic tweet-engagement dataset, while the current local demo uses a schema-compatible synthetic generator because the original external dataset is not shipped with the submission.

The main contributions are: (i) a reproducible Docker Compose environment with Kafka, Spark, Qdrant, embedding workers, and a Scala API; (ii) a RecSys-schema-compatible producer whose records contain real multilingual BERT token IDs; (iii) a Spark cleaner that parses TSV records, validates them, decodes WordPiece tokens, and deduplicates tweets; (iv) a vector retrieval and ranking layer that exposes semantic, recency, and final scores; and (v) scripts that demonstrate distribution across Kafka partitions, Spark workers, and embedding consumers.

\section{Related Work}
Content-based recommendation systems represent users and items through item attributes and recommend items similar to the user's profile \cite{pazzani2007content}. Hybrid recommenders combine content-based and collaborative signals to improve coverage and accuracy \cite{burke2002hybrid}. Large industrial recommenders commonly separate candidate generation from ranking; for example, YouTube's recommender uses a retrieval stage followed by a ranking stage \cite{covington2016youtube}. DistribuTweet mirrors this separation at a smaller scale: Qdrant retrieves semantically similar candidates, and the API applies a lightweight ranking formula.

The stream-processing architecture builds on well-known distributed systems. Kafka provides a durable publish-subscribe log for decoupling producers and consumers \cite{kreps2011kafka}. Spark provides a unified engine for distributed data processing \cite{zaharia2016spark}. DistribuTweet uses Kafka for the raw and cleaned post streams and Spark Structured Streaming for validation, token decoding, and deduplication.

Semantic retrieval relies on dense sentence representations. Sentence-BERT showed that transformer-based encoders can generate sentence embeddings suitable for efficient similarity search \cite{reimers2019sentencebert}. The implementation uses the multilingual MiniLM sentence-transformer model, producing normalized 384-dimensional vectors. Qdrant stores these vectors and supports cosine search over a collection \cite{qdrantdocs}. The input schema is based on the Twitter-provided RecSys Challenge 2021 dataset, which focuses on tweet engagement prediction and fairness-aware recommendation \cite{recsys2021challenge}.

\section{Implementation Details}
\subsection{RecSys-Compatible Data Source}
The project targets the RecSys Challenge 2021 Twitter schema rather than inventing a private format. The original dataset contains tokenized tweet text, user metadata, tweet metadata, and engagement-related fields \cite{belli2021recsys}. Since the full external dataset is large and not bundled with the project, the submitted implementation includes a synthetic generator that follows the same twenty-column TSV schema and field order.

The generator creates tweet-like records from topic pools such as technology, sports, music, food, travel, gaming, science, finance, health, and art. It uses \texttt{bert-base-multilingual-cased} tokenization, so the \texttt{text\_tokens} field contains real multilingual BERT token IDs, matching the important privacy-preserving characteristic of the RecSys data. The producer also includes an optional file mode, \texttt{--input-tsv}, so if a compatible RecSys TSV file is available, the rest of the pipeline can process file rows without changing Kafka, Spark, embedding, Qdrant, or API code.

\subsection{Kafka Ingestion}
The \texttt{data-generator} service writes TSV records to \texttt{posts.raw}. Kafka is configured with explicit topic creation and three partitions to demonstrate partitioned ingestion. The producer uses the tweet ID as the Kafka key, giving stable partitioning and making duplicates observable downstream. The default data generation rate is configurable through \texttt{RATE\_PER\_SEC}, and \texttt{TOTAL\_MESSAGES=0} means continuous generation.

\subsection{Spark Cleaning and Token Decode}
The Spark cleaner consumes \texttt{posts.raw}. It parses each TSV row according to the RecSys schema, rejects malformed records, validates required fields, decodes BERT token IDs back into text using a broadcast \texttt{vocab.txt}, and removes duplicate tweet IDs with event-time watermarking. The cleaner writes accepted records as JSON to \texttt{posts.cleaned}. Its responsibility is deliberately limited to data preparation; it does not make recommendation decisions.

\subsection{Embedding Workers and Qdrant}
The embedding workers consume \texttt{posts.cleaned} using a shared Kafka consumer group. Each valid cleaned post is embedded with \texttt{paraphrase-multilingual-MiniLM-L12-v2}. Vectors are normalized and written to the Qdrant \texttt{posts} collection with cosine distance and size 384. The same Python image also runs as a single HTTP embedding service on port 8000 with consumer mode disabled; the Scala API calls this service when it needs to embed user interest phrases.

\subsection{Recommendation API}
The API runs on port 8081 and exposes:

\begin{itemize}
\item \texttt{POST /users/\{userId\}/interests}: creates a user profile from interest phrases.
\item \texttt{GET /users/\{userId\}/feed?limit=20}: returns a personalized feed.
\item \texttt{GET /health}: returns service health.
\end{itemize}

For profile creation, each interest phrase is embedded, the vectors are averaged, and the average is normalized. For feed retrieval, the API searches Qdrant for similar posts and reranks the candidates.

\section{Recommendation Method}
Let \(\mathbf{e_i}\) be the embedding of interest phrase \(i\). The user profile vector is:

\begin{equation}
\mathbf{u} =
\frac{\frac{1}{n}\sum_{i=1}^{n}\mathbf{e_i}}
{\left\|\frac{1}{n}\sum_{i=1}^{n}\mathbf{e_i}\right\|_2}.
\end{equation}

Qdrant returns cosine similarity scores. The API maps cosine similarity from \([-1,1]\) to \([0,1]\):

\begin{equation}
semantic = \frac{cosine + 1}{2}.
\end{equation}

Recency is computed with exponential decay:

\begin{equation}
recency = e^{-\frac{ageHours}{24}}.
\end{equation}

The final score is:

\begin{equation}
finalScore = 0.85 \cdot semantic + 0.15 \cdot recency.
\end{equation}

The weights are intentionally simple and configurable. This makes the prototype explainable during the demo: every feed item exposes its semantic similarity, recency score, and final score. The feed layer also removes near-duplicate text variants using Jaccard similarity over word sets, preventing visually repetitive feeds when different records contain almost identical content.

\section{Evaluation and Demonstration}
\subsection{Functional Demo}
The main demonstration starts all services with:

\begin{verbatim}
docker compose up -d --build
\end{verbatim}

The \texttt{data-generator} begins producing RecSys-schema-compatible records. The \texttt{scripts/demo.sh} script then walks through the full system: production, Kafka partition distribution, Spark cleaning, embedding worker group status, Qdrant vector count, and three feed examples for different interest profiles. Health and verification are available through \texttt{scripts/smoke-test.sh}. The distribution proof script, \texttt{scripts/show-distribution.sh}, displays Kafka partition assignment and worker distribution.

\subsection{Observed Behavior}
The system demonstrates that content-based semantic search can separate topic clusters without using a follow graph. For example, technology interests should return technology-like posts, while food-related interests should return cooking or coffee-related posts. Because the embedding model is multilingual, Turkish interests can retrieve semantically related posts in other languages when the generated stream contains them.

\subsection{Tests}
The Scala test suite covers RecSys TSV parsing, validation behavior, WordPiece decoding, ranking score calculations, and deterministic fingerprint behavior. The Docker build includes these tests, so broken core logic prevents image creation. The project also provides smoke tests for the running Compose environment.

\section{Deployment}
Docker Compose is the primary target. The environment starts Kafka, Qdrant, Spark master, two Spark workers, Spark cleaner, data generator, two embedding workers, one embedding API, and the recommendation API. The exposed interfaces include the Spark master UI at port 8080, Spark application UI around port 4040, Qdrant dashboard at port 6333, embedding health at port 8000, and recommendation API at port 8081.

The implementation is pseudo-distributed: all containers run on one machine, but the software boundaries match a horizontally scalable design. Kafka can repartition topics, Spark can run additional workers, embedding workers can be scaled with Docker Compose, and the API can be replicated because durable state is stored outside the process.

\section{Limitations}
DistribuTweet does not train a learned ranking model. It does not use collaborative filtering, impression history, authentication, moderation, or private production features. The generator follows the RecSys schema and tokenization behavior, but the local data are synthetic unless a compatible TSV file is supplied through the producer's file mode. Therefore, the evaluation demonstrates system correctness and architectural scalability, not production recommendation quality. Also, the original RecSys task includes engagement and fairness objectives that are not yet optimized by this content-based prototype.

\section{Conclusion and Future Work}
This project implements a working pseudo-distributed semantic recommendation pipeline for tweet-like streams. Kafka decouples services, Spark cleans and decodes RecSys-style records, the embedding workers index multilingual vectors, Qdrant provides vector retrieval, and the Scala API serves personalized feeds with explainable scores.

Future work should use real RecSys TSV files when available, incorporate engagement labels, train a ranking model, add impression history, evaluate ranking metrics such as NDCG, add stronger diversity controls, monitor latency and Kafka lag, and test a multi-node Kubernetes deployment.
